How guest LAN egress works now

OVN 26.03 gateway-router SNAT, the options:chassis requirement, and how qlvm install keeps it correct. Verified live on dom0 (OVN 26.03.2-122.fc44, Xen 4.21) — 2026-10-08. Working example: VM foo, 10.100.1.10, vif vif13.0.

TL;DR. Guest VMs reach the LAN through the OVN gateway router: traffic leaves the work logical switch, is routed by the gateway router, and is SNATed from 10.100.0.0/16 → 172.31.12.200 before crossing the localnet port onto br-ex. OVN 26.03 silently skips NAT flow generation for any router whose options:chassis is empty — the old config had none, so the SNAT simply vanished and guest egress died. The fix is forward, not a workaround: qlvm install now reads the live chassis name from the OVN southbound Chassis table and pins options:chassis on the gateway router — at create time and as an in-place drift repair on every re-run.

1. What broke, and why it was silent

On Oct 5, 09:56 the dom0 picked up ovn-26.03.2-122.fc44 (from 25.09.2). From then on: dom0 → VM worked, guest → dom0 and guest → LAN did not (pings left the guest but replies never came back; DNS answered "no servers could be reached"). Everything else was verifiably correct — OVN NB config right, guest networkd up on enX0, firewall out of the picture (inactive).

The cause is a behavior change inside ovn-northd (the compiler from northbound config to logical flows):

OVN 25.09 (worked)

northd derived "is this a gateway router?" from the topology: a router with a localnet-attached peer port was treated as a gateway router. Its NAT rows were compiled into flows automatically. No explicit option was ever needed — qlvm's config never set one.

OVN 26.03 (broke) — silent failure

// northd/northd.c:5364 (full-rebuild
// path repeats at :955)
od->is_gw_router =
  !!smap_get(&od->nbr->options,
             "chassis");

// NAT builder guard, ~:18198
if (!od->is_gw_router &&
    vector_is_empty(&od->l3dgw_ports))
  return;  /* no NAT flows,
              no log line */

is_gw_router is now decided by Logical_Router.options:chassis being non-empty. Empty options → the builder early-returns → zero NAT flows, no error, no log. The router's NAT row still sits in the NB database looking perfectly healthy.

Why it looked like a routing or firewall problem: with no SNAT, guest egress packets left the LAN carrying their private source (e.g. 10.100.1.10). The LAN has no route for 10.100.0.0/16, so replies were dropped upstream — exactly the symptom of a dead return path. The dom0 itself was unaffected because its own traffic never needed the NAT.

Fig. 1 — The one-line behavior change. Topology is unchanged across versions; only the trigger for NAT compilation moved from "derived from the localnet peer" to "explicit option". Northd only checks the option for presence, but qlvm stores the real chassis name so the value stays honest and auditable.

Reference implementation: ovn-kubernetes runs this exact OVN build in production and does precisely this — go-controller/pkg/ovn/gateway.go (lines 285–295) sets "chassis": gwConfig.annoConfig.ChassisID on the gateway router's options. Its multi-node chassis pinning (gateway_chassis/ha_chassis_group on the LRP) is not needed on a single-chassis dom0; options:chassis alone is sufficient (live-verified). For completeness: 26.03 also redefined the per-port check lrp_is_l3dgw() (northd.h:1132) to require a chassis/HA group, and NAT validation moved to northd/en-lr-nat.c — neither matters here with the option set.

3. The dom0's own traffic (and why the purple path still exists)

Two different directions, two different paths:

  • dom0 → guest (e.g. ssh user@10.100.1.10, qlvm vm run): the dom0 kernel has a direct route 10.100.1.0/24 dev qvm-dom0. qvm-dom0 is a kernel netdev backed by an OVS internal port on br-int, and the dom0 LSP (10.100.1.2) attaches it straight to the work switch — no router, no NAT, ttl=64. This is the low-latency control path.
  • guest → dom0 (e.g. the guest's waypipe server dialing the dom0's ephemeral data port for qlvm vm run --connect tcp|vsock): this is guest egress, so it takes the router path ①–⑥ and arrives at the dom0 with source 172.31.12.200 (the SNAT address), not 10.100.1.10. That is why the dom0's firewall dom0-data-in policy rich-rules match the router IP for the data port range, and why network.dom0_ip in qlvm.yaml must be the dom0's uplink address (br-ex), not the router IP.

The qvm-dom0 join is still manual (an OVS port + LSP + kernel route, not yet owned by the qlvm reconcilers) — it predates this fix and is orthogonal to it: even with SNAT working, dom0→guest via the router would be asymmetric and slower. Persisting it in the reconcilers remains the follow-up.

4. What qlvm install does now

Fig. 3 — The install flow. The SB client is read-only: it exists only to answer "what chassis name is live right now?". Everything it writes is one option on one row; northd does the rest. The bottom box is the actual live verification sequence.

Implementation notes (the non-obvious parts)

  • Two condition/mutation models. libovsdb's Where(model) derives the match clause from the model's non-zero fields. If the new option value sat on the same model, the match would be "options already equals the new value" — which is false on a broken row, so the mutate would silently no-op. The repair therefore builds a bare condition model (UUID only) and a separate value model.
  • count=1 is not proof. Both the in-memory test server and the real one answer the mutate with count=1, but the Go client's List reads the monitor cache, which lags the write. Verify effects server-side (ovn-nbctl get) and in the SB flows — never from the client cache a few milliseconds after the Transact.
  • The steady-state early exit was the second bug. The original Apply returned before the attach pass when nothing was missing — so a steady-state re-run could never repair a drifted option. The attach pass now always runs, and "no ops at all" is the only no-op path (this also means a fresh-install transaction is still exactly one atomic batch).
  • Why the chassis name, not a literal. Northd only checks presence, but storing the real name from the SB Chassis table keeps the row truthful (and matches what ovn-kubernetes does). On a single-chassis dom0 the name is stable across reboots (it's the chassis's own UUID).
  • Install re-run hardening found along the way: the ovs step used to wait 30 s for a DHCP lease on the bare NIC, but in the already-migrated state the NIC is enslaved (master ovs-system) and may legitimately hold no lease anymore. The wait is skipped when netd.Enslaved() sees a kernel master; the bridge-lease check + failback still guard the uplink.

Logical flows northd compiled once the option was set

$ sudo ovn-sbctl dump-flows gateway

  priority = 90

26.03 has no SB NAT table — northd compiles NAT directly into Logical_Flow rows (validation in northd/en-lr-nat.c, flow generation in northd.c 17614–17778; encode_ct_nat in lib/actions.c lowers ct_snat to OVS ct(…, nat(src=…))).

Physical OVS flows on br-int (what the hardware actually executes)

$ sudo ovs-ofctl dump-flows br-int table=51 | grep 10.100
  ct_state=-trk, ip, metadata=0x3, nw_src=10.100.0.0/16
  actions=ct(commit, table=52, zone=NXM_NX_REG12[0..15], nat(src=172.31.12.200))

# table 13 carries the ingress mirror (unsnat)
# conntrack zones (ovn-controller): gateway_snat=2, gateway_dnat=3, work_snat=1

Table numbers moved in 26.03: lr_out_snat is physical table 51 (it was 25 in 25.09). The pipeline is expanded; always resolve the number from the table comment (ovs-ofctl dump-flows br-int | grep "table=51.*snat" style) rather than remembering it.

End-to-end test from the guest

$ ssh user@10.100.1.10
$ ping -c3 172.31.12.234          # LAN server through the OVN SNAT
3 packets transmitted, 3 received, 0% packet loss
$ host -t A www.google.com        # DNS through the same path

Controlled experiment: the dom0-side MASQUERADE stopgap (iptables NAT on br-ex) was removed after the options:chassis fix and the guest kept working — proving the OVN SNAT path alone carries guest egress. No dom0 NAT rule is part of the design anymore.

The install re-run re-pins the option and is the first thing to try. (The reverse skew — builder Xen headers vs dom0 runtime — is a separate, build-time constraint; see AGENTS.md.)
