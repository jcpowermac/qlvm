## 1. `qlvm vm run` running-check (DONE — committed `85e78a2`)

**Intent:** `vm run` used to silently hang in waypipe when the VM's domain
wasn't actually serving. Now it gates on the domain's *state* (not just
existence), so a stopped, paused, or zombie (`---sr-`) VM fails fast with a
recovery command.

**Changed files** (all in `internal/cli/`):
- `run.go` — new `assertVMRunning(name)` called in `runCmd` RunE right after
  `LoadMeta`, before the token/connect checks reach `projection.Run`.
- `run_test.go` — `TestAssertVMRunning` (running OK, blocked OK, absent →
  "not running — qlvm vm start", dying → zombie/restart hint, paused →
  "VM is paused", stub-build skip when `xenctlNew` fails).
- `lifecycle_test.go` — `fakeXen` gained `domains []xenctl.DomainInfo` and
  `List()` returns it (was hardcoded `nil, nil`).

**State semantics** (from `xenctl.domainState`; dying takes precedence):
| Xen state | gate result |
|---|---|
| `running`, `blocked` | allowed (blocked = idle vCPU, guest provably live) |
| `dying` (the `---sr-` zombie) | error → `qlvm vm restart <name>` |
| `paused`, `stopped` | error → `qlvm vm start <name>` |
| domain absent | error → `qlvm vm start <name>` |
| `xenctlNew` fails (stub build, no libxl) | check skipped, `run` proceeds |

**Verification:** `go test -tags "exclude_graphdriver_btrfs exclude_graphdriver_zfs
containers_image_openpgp" ./internal/...` all pass (bare `go build ./...`
fails on missing gpgme/btrfs headers — use the tags).

**Outstanding:** live-verify requires `sudo make container-build` (the
`bin/qlvm` stub can't talk to Xen). Expect: run on a stopped VM → instant
error; run on a `---sr-` zombie → "VM is a zombie … qlvm vm restart"
instead of a hang.

**Follow-up not done (skipped by design):** auto-start on demand from `run`;
zombie auto-recovery.

## 2. iGPU SR-IOV VF → Xen guest, no QEMU

**Goal:** present the dom0's integrated GPU to qlvm VMs via SR-IOV VFs without
QEMU, for guest-side media decode/compute. Display stays on the dom0 (VFs are
compute/decode only; physical display would require passing `00:02.0` itself,
which kills the dom0's display + all VFs).

### Verdict
Mechanically possible with **no QEMU anywhere**: Xen PCI passthrough to
PV/PVH guests goes through **pciback** (IOMMU-backed PV-style assignment);
QEMU is only in the picture for *HVM* guests, and qlvm domains are hard-PVH
(`LIBXL_DOMAIN_TYPE_PVH`, `internal/xenctl/xenctl_cgo.go:59,61`). End state:
one `libxl_device_pci` entry per VF + a `PCI []string` on `DomainSpec`.
Unverified sub-claim: one third-party wiki says "PCI passthrough not supported
with PVH as of Xen 4.20" — contradicted by Qubes-class PVH+passthrough
practice; settle it with the scratch-domain smoke (step 4 below), cost is one
scratch domain.

### This dom0, verified live (2026-10-03; see §3 for post-reboot state)
| check | result |
|---|---|
| iGPU | **Arrow Lake-S** `00:02.0 [8086:7d67]` rev 06; PCIe cap advertises **7 VFs** (`sriov_totalvfs=7`, `sriov_numvfs=0`) |
| owner | **i915** bound (driver symlink); `echo 1 > sriov_numvfs` → rc=1, dmesg `i915 …: driver does not support SR-IOV configuration via sysfs` (root cause found 2026-10-04, §3) |
| in-tree xe (F44 kernel 7.2.x) | **dead end**: grepped `/lib/modules/…/xe/xe.ko.xz` — **zero** `7d67`/`7d55` PCI ID-table entries, so xe can't bind the device even with `force_probe`. In-tree `has_sriov` covers TGL/ADL/PTL/BMG/etc.; ARL/MTL upstream SR-IOV is "not ready" (dri-devel 2025-07 status + issue #359 maintainer) |
| VT-d | was **OFF** pre-reboot; kargs in post-reboot — IOMMUs visible in dmesg; `/sys/kernel/iommu_groups` empty, which is expected under Xen (dom0 device model) — §3 |
| vfio-pci | available (modprobe OK, not loaded) |
| dom0 stack | ostree/atomic, Xen 4.21.2 (`/proc/xen/capabilities: control_d`), no ad-hoc dnf on host — packages belong in `../os/recipes/recipe.yml` |

**Key repo:** [strongtz/i915-sriov-dkms](https://github.com/strongtz/i915-sriov-dkms)
(ekartashov/xe-sriov is the same tree). Ships SR-IOV-patched **i915 and xe**
modules. **Release 2026.09.16 supports kernel 6.17–7.2 → builds
against this dom0's 7.2.8 and F44 guests.** The **same driver must run in
the guest**, not the in-tree one (`docs/install-linux-guest.md`: "We will
need to run the same driver under Linux guests" — in-tree 7.2 i915/xe have
no ARL SR-IOV VF device IDs, so a stock guest can't bind a passed-through
VF; the README's "host/guest module versions need not match" is about
version skew only). Its README's "required kernel 6.12–6.18" line is stale
(older release).

**Same-device issue: [#359 — Arrow Lake (7d67) SR-IOV](https://github.com/strongtz/i915-sriov-dkms/issues/359).**
- VFs create fine; the reported `VFIO_MAP_DMA` failure was on the **QEMU**
  path, kernel 6.14-era (works 6.17+) — may not affect Xen pciback at all.
- Working cmdline from the thread (xe flavor): `intel_iommu=on iommu=pt
  video=efifb:off xe.force_probe=7d67 i915.force_probe=!7d67 xe.max_vfs=7`;
  i915 flavor: `intel_iommu=on i915.enable_guc=3 i915.max_vfs=7
  module_blacklist=xe` (+ force_probe as needed).
- **Stability risk: hard-locks 24–48h after SR-IOV is initialized, even with
  no VM running** (multiple reporters, MTL/ARL). Linux guests work
  (compute/decode); Windows has regressions. A pending GGTT-relay patch series
  (PR #415) targets MTL/ARL gaps.

### Root cause — **SUPERSEDED, see §7.**
The conclusion below ("conditionally registered at load time … no initramfs
problem; udev loads `extra/i915.ko.xz` post-pivot") was **wrong**: on the
boots after 2026-10-04 with the full karg set, the running module STILL had
no `max_vfs` (dmesg `i915: unknown parameter 'max_vfs' ignored` at ~8 s —
pre-pivot, i.e. loaded from the initrd, not udev). The real chain: dkms
install put the modules in `updates/`/`extra/` but **depmod never ran**, so
`modules.dep` had no GPU entries and dracut `--no-hostonly` (copies from
modules.dep) kept the old display-only i915 in the initrd, which loads
pre-pivot and shadows the patched one. Fix: §7 (os `e38b961`).

**Lessons paid for in this session (don't re-derive):**
- **dom0 initrds here have a zstd-compressed main cpio** (microcode cpio
  plain at offset 0, zstd magic at ~17084416). Fixed-offset `cpio -t` and
  `grep -a "path.ko"` probes on the raw bytes are GARBAGE. Decompress:
  `tail -c +17084417 initrd | zstd -d | cpio -t`. (This poisoned ~2 h of
  "is i915 in the initrd?" forensics; both answers — yes/no — were wrong.)
- **Plain dracut does not embed out-of-tree `/lib/modules/<kver>/extra/`
  modules.** The `45drm` dracut module finds KMS drivers by *symbol scan of
  the kernel tree only* (`dracut_instmods -o -s "drm_crtc_init|…" 
  =drivers/gpu/drm`). That's how the pre-dkms image initramfs got stock
  i915/xe baked in, and why post-dkms initrds get none. `--add-drivers`
  (space-separated! comma-sep is passed as one literal name and fails) DOES
  embed them, but is unnecessary here — rootfs loading works (this boot
  proves it).
- The old `modinfo | grep param:` miss: the field is `parm:` in current
  kernels; the "0 params" reading that started this whole mystery was a
  grep bug.

## 5. INCIDENT 2026-10-03 ~21:56 — dom0 booted native, "Xen is broke"

**What happened.** After staging 44.20261003.0 (kernel 7.2.8) and rebooting,
the dom0 came up WITHOUT Xen (no hypervisor flag in /proc/cpuinfo,
`BOOT_IMAGE=(hd0,gpt2)` in /proc/cmdline, `xl` = "no privileged command
interface"). All VMs (foo) died with the host. The boot came from the BLS
entry `ostree-2.conf` (the staged deployment's title, "44.20261003.0
(ostree:0)") — a NATIVE Linux entry, not the hand-rolled Xen menuentry.

**Root cause (why xen-dom0-refresh did not prevent it).**
- The unit itself worked: it fired at boot (21:56:50) and wrote a correct
  user.cfg. It just cannot stop GRUB from being *offered* a second boot
  path: ostree staged updates rewrite `/boot/loader/entries/` (at
  `ostree-finalize-staged` on shutdown) with native BLS entries. Picking
  one — manually at the menu, or by any future default mechanism — boots
  the dom0 without Xen.
- There is no grubenv override on this box: ostree (2026.4, verified via
  strings on libostree) never touches grubenv; the coreos-assembler
  grub.cfg has no next_entry/saved_entry handling; no grub2-editenv
  activity in the journal. So the entry was selected at the interactive
  GRUB menu (someone was at the console). The Xen entry WAS menu item 0
  and the auto-boot default — waiting out the 5 s timeout would have booted
  Xen fine.
- Latent script bug (fixed): section 4 matched `ostree admin status`
  deployment checksums against `/ostree/boot.N/fedora/<dir>` names — but
  boot trees are named by the **bootconfig tree's checksum**, a different
  namespace (deployment 06837770… vs boot dir 3024645a…). The match never
  succeeded; user.cfg always used the /proc/cmdline fallback. Fine in
  steady state (it tracks the booted tree), but it never tracked the
  deployment at finalize time.

**Fix (applied 2026-10-03, machine-local, later committed to the os repo):**
- `/usr/local/sbin/xen-dom0-refresh` rewritten:
  - default-deployment target = `ostree admin status --json` deployments[0]
    (staged or booted — always what boots next), mapped to its boot tree by
    resolving `/ostree/boot.0/fedora/<boottree>/0` symlinks (each points at
    the deployment dir; boot-tree names are bootconfig-tree checksums, a
    different namespace from deployment commits). Kernel/initrd hardlinks
    come from the matching `/boot/ostree/fedora-<boottree>/` payload.
    Deliberately scans boot.0 ONLY: pre-finalize the staged tree is under a
    fresh boot.N and its kernel isn't on the boot partition yet, so the
    finalize hook (post boot.0 swap) is the moment both become true; a
    crash between stage and finalize keeps the last-good Xen entry instead
    of dangling. No BLS parsing (BLS is ostree's rendering of the same
    mapping, and is only rewritten at finalize). Fallbacks: uname-r
    /boot/ostree scan, then cmdline ostree=.
  - user.cfg now also emits `set default=0` (forced, after load_env) so the
    auto-boot always takes the Xen entry even if grubenv ever carries a
    default/next override.
- NEW hook: `/etc/systemd/system/ostree-finalize-staged.service.d/10-xen-dom0-refresh.conf`
  adds `ExecStopPost=/usr/local/sbin/xen-dom0-refresh`. That unit runs its
  finalize as ExecStop (RemainAfterExit=yes oneshot) during the shutdown
  transaction — so the refresh now runs at EXACTLY the moment ostree swaps
  BLS + boot.N, while the system can still execute. The .path/.service
  units stay as-is (staging + boot coverage).
- Verified pre-reboot: user.cfg → ostree=/ostree/boot.0/fedora/3024645a…/0
  (= booted deployment), /boot/xen-dom0 inodes 29/30 = 7.2.8 payload.
  Selection-logic self-test passed for current/rollback/no-marker layouts.

**Still true:** the BLS entries remain in the GRUB menu (ostree-owned,
regenerated at every finalize). Manually selecting one boots the dom0
native again — deliberate tradeoff (removing them = one `rm` in the
finalize hook if the footgun class is ever unacceptable).

- Deployment `modules.dep` had **zero GPU entries**: `depmod` was never run
  on the tree after the modules were placed in `updates/`/`extra/`.

### Root cause (correct version)
blue-build has **no `dkms` module**; the old recipe ran `dkms install` in a
`script` step. strongtz's `dkms.conf` sets `DEST_MODULE_LOCATION[0-3]=/updates`
and nothing in the ostree build container runs depmod afterward (the kernel
install hooks that would are shimmed/absent). The `initramfs` module then
runs `dracut --no-hostonly --reproducible` — and `--no-hostonly` installs
**every module listed in `modules.dep`**, so a tree that never ran depmod
contributes nothing: the initrd kept the display-only i915 from the base
image, which loads pre-pivot and shadows the patched module post-pivot
(modprobe on an already-loaded module is a no-op).

### Research trail (don't re-derive)
- **blue-build `akmods` module = cache consumer, not a builder.** Its script
  hardcodes `skopeo copy docker://ghcr.io/ublue-os/akmods:<base>-<fedora>`,
  extracts `kmod-*.rpm`s and `rpm-ostree install`s them; options are only
  `base`/`install`/`nvidia-driver`. Ublue's kmod list (akmods repo README +
  Containerfile): common = openrazer, v4l2loopback, vhba, wl, xone, xpadneo,
  zfs, nvidia; extra = gcadapter_oc, nct6687d, zenergy, ryzen-smu, evdi,
  system76(-io), hid-tmff2, new-lg4ff, t150-driver, hid-fanatecff, sc0710,
  ayaneo-leds, kvmfr. **No i915** — using the built-in module for our driver
  would require upstreaming a build into ublue's CI/cache.
- **The akmods pattern** (aurora `build_scripts/base/02-install-common-kernel-akmods.sh`
  + `19-initramfs.sh`; bazzite `build_files/install-kernel-akmods` +
  `build-initramfs`; blue-build `initramfs` module source): versionlock
  kernel+kernel-devel → shim `/usr/lib/kernel/install.d/{05-rpmostree,50-dracut}.install`
  → install modules into the module tree (ublue: pre-built signed kmod RPMs;
  Fedora's `akmods` CLI: builds the akmod SRPM and lands .ko in
  `weak-updates/`) → **depmod** → explicit `dracut --no-hostonly --reproducible`
  as the LAST step. `weak-updates/` has higher modprobe priority than any
  kernel-tree copy — that's what stops a stock i915 shadowing the patched
  one.
- **strongtz tree builds without dkms**: top-level `Makefile` (kbuild
  subdir style), modules at `drivers/gpu/drm/i915/{i915,kvmgt}.ko` +
  `drivers/gpu/drm/xe/xe.ko` + `compat/intel_sriov_compat.ko` per its
  `dkms.conf` `BUILT_MODULE_LOCATION` entries. `BUILD_EXCLUSIVE_KERNEL
  ^(7.[0-2]|6.1[7-9])` — matches our 7.2.8.

### Fix (os commit `e38b961`, pushed; build run 37224517843 = SUCCESS 9m49s)
`recipes/recipe.yml`: the dkms `script` step is replaced by two snippets —
(1) clone strongtz tag 2026.09.16, (2) `make -C /usr/src/kernels/<kver>
M=$PWD modules`, `install -m 644` the four .ko into
`/usr/lib/modules/<kver>/weak-updates/`, `depmod -a <kver>`, then fail-fast

Image `ghcr.io/jcpowermac/os:latest` now carries the fix.
- **Guest side (`bolt.yml`) intentionally unchanged**: it still uses the dkms
  flow, which is correct *for the guest* — the F44 7.2 kernel ships **no
  in-tree i915**, so nothing can shadow the dkms module there (the dom0
  problem was the base image's stale display-only i915 in its initrd). Verify
