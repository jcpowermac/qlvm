## 1. `qlvm vm run` running-check (DONE — uncommitted)

**Intent:** `vm run` used to silently hang in waypipe when the VM's domain
wasn't actually serving. Now it gates on the domain's *state* (not just
existence), so a stopped, paused, or zombie (`---sr-`) VM fails fast with a
recovery command.

**Changed files** (`git status` — all in `internal/cli/`):
- `run.go` — new `assertVMRunning(name)` called in `runCmd` RunE right after
  `LoadMeta`, before the token/connect checks reach `projection.Run`.
- `run_test.go` — `TestAssertVMRunning` (running OK, blocked OK, absent →
  "not running — qlvm vm start", dying → zombie/restart hint, paused →
  "VM is paused", stub-build skip when `xenctlNew` fails).
- `lifecycle_test.go` — `fakeXen` gained `domains []xenctl.DomainInfo` and
  `List()` returns it (was hardcoded `nil, nil`).

**State semantics** (from `xenctl.domainState`; dying takes precedence):
| Xen state | gate result |
|---|---|
| `running`, `blocked` | allowed (blocked = idle vCPU, guest provably live) |
| `dying` (the `---sr-` zombie) | error → `qlvm vm restart <name>` |
| `paused`, `stopped` | error → `qlvm vm start <name>` |
| domain absent | error → `qlvm vm start <name>` |
| `xenctlNew` fails (stub build, no libxl) | check skipped, `run` proceeds |

**Verification:** `go test -tags "exclude_graphdriver_btrfs exclude_graphdriver_zfs
containers_image_openpgp" ./internal/...` all pass (bare `go build ./...`
fails on missing gpgme/btrfs headers — use the tags).

- Live-verify requires `sudo make container-build` (the `bin/qlvm` stub can't

## 2. iGPU SR-IOV VF → Xen guest, no QEMU (RESEARCH ONLY — not started)

**Goal:** present the dom0's integrated GPU to qlvm VMs via SR-IOV VFs without
QEMU, for guest-side media decode/compute. Display stays on the dom0 (VFs are
compute/decode only; physical display would require passing `00:02.0` itself,
which kills the dom0's display + all VFs).

### Verdict
Mechanically possible with **no QEMU anywhere**: Xen PCI passthrough to
PV/PVH guests goes through **pciback** (IOMMU-backed PV-style assignment);
QEMU is only in the picture for *HVM* guests, and qlvm domains are hard-PVH
(`LIBXL_DOMAIN_TYPE_PVH`, `internal/xenctl/xenctl_cgo.go:59,61`). End state:
one `libxl_device_pci` entry per VF + a `PCI []string` on `DomainSpec`.
Unverified sub-claim: one third-party wiki says "PCI passthrough not supported
with PVH as of Xen 4.20" — contradicted by Qubes-class PVH+passthrough
practice; settle it with the scratch-domain smoke (step 4 below), cost is one
scratch domain.

### This dom0, verified live (2026-10-03)
| check | result |
|---|---|
| iGPU | **Arrow Lake-S** `00:02.0 [8086:7d67]` rev 06; PCIe cap advertises **7 VFs** (`sriov_totalvfs=7`, `sriov_numvfs=0`) |
| owner | **i915** bound (driver symlink); `echo 1 > sriov_numvfs` → rc=1, dmesg `i915 …: driver does not support SR-IOV configuration via sysfs` |
| in-tree xe (F44 kernel 7.2.7-200) | **dead end**: grepped `/lib/modules/…/xe/xe.ko.xz` — **zero** `7d67`/`7d55` PCI ID-table entries, so xe can't bind the device even with `force_probe`. In-tree `has_sriov` covers TGL/ADL/PTL/BMG/etc.; ARL/MTL upstream SR-IOV is "not ready" (dri-devel 2025-07 status + issue #359 maintainer) |
| VT-d | **OFF**: no `intel_iommu=` in `/proc/cmdline`, `/sys/kernel/iommu_groups` empty (only legacy "VT-d active for gfx access" line). Hard requirement for passthrough |
| vfio-pci | available (modprobe OK, not loaded) |
| dom0 stack | ostree/atomic, Xen 4.21.2 (`/proc/xen/capabilities: control_d`), no ad-hoc dnf on host — packages belong in `../os/recipes/recipe.yml` |

**Key repo:** [strongtz/i915-sriov-dkms](https://github.com/strongtz/i915-sriov-dkms)
(ekartashov/xe-sriov is the same tree). Ships SR-IOV-patched **i915 and xe**
modules. **Release 2026.09.16 (5 days old) supports kernel 6.17–7.2 → builds
against this dom0's 7.2.7 and F44 guests.** The **same driver must run in
the guest**, not the in-tree one (`docs/install-linux-guest.md`: "We will
need to run the same driver under Linux guests" — in-tree 7.2 i915/xe have
no ARL SR-IOV VF device IDs, so a stock guest can't bind a passed-through
VF; the README's "host/guest module versions need not match" is about
version skew only). Its README's "required kernel 6.12–6.18" line is stale
(older release).

**Same-device issue: [#359 — Arrow Lake (7d67) SR-IOV](https://github.com/strongtz/i915-sriov-dkms/issues/359).**
- VFs create fine; the reported `VFIO_MAP_DMA` failure was on the **QEMU**
  path, kernel 6.14-era (works 6.17+) — may not affect Xen pciback at all.
- Working cmdline from the thread (xe flavor): `intel_iommu=on iommu=pt
  video=efifb:off xe.force_probe=7d67 i915.force_probe=!7d67 xe.max_vfs=7`;
  i915 flavor: `intel_iommu=on i915.enable_guc=3 i915.max_vfs=7
  module_blacklist=xe` (+ force_probe as needed).
- **Stability risk: hard-locks 24–48h after SR-IOV is initialized, even with
  no VM running** (multiple reporters, MTL/ARL). Linux guests work
  (compute/decode); Windows has regressions. A pending GGTT-relay patch series
  (PR #415) targets MTL/ARL gaps.
