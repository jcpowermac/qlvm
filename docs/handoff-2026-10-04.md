## 10. CORRECTION, later the same night — §3's root cause is refuted. The plain blobs ARE the bug

The reboot happened. §8's checklist came back: srcversion ✓ `909F33CF13511056FB511A7`
(loaded `i915` matches), blobs present ✓ (`mtl_guc_70.bin` 320320 B, sha256 ==
`xz -dc` of the `.xz`), login prompt ✓ — but still `fetch failed -EACCES` →
`GuC initialization failed -ENOEXEC` → `GT0: Enabling uc failed (-5)` → **GT wedged** →
`IOV: Initialization failed (-EIO)` → `No VFs could be associated`, `sriov_numvfs = 0`.
**Do not re-derive §1–§5; three things in that diagnosis are wrong, each shown by a
command, not a theory:**

1. **The blob was never missing.** `rpm -qf /usr/lib/firmware/i915/mtl_guc_70.bin.xz` →
   `intel-gpu-firmware-20260916-1.fc44`, and
   `sudo ostree ls e643c7bd… /usr/lib/firmware/i915` lists `mtl_guc_70.bin.xz` +
   `mtl_huc_gsc.bin.xz` in the *previous* deployment too. §3 checked only the
   uncompressed name and concluded "no linux-firmware RPM in the image has it, in any
   deployment". That premise was false.
2. **The success criterion proves nothing.** `print_fw_ver()`
   (`drivers/gpu/drm/i915/gt/uc/intel_uc.c:431`) emits the *expected* version from the
   driver's own `file_selected` table at the top of `__uc_init_hw()` regardless of what
   the fetch did — it printed in the very boot where the fetch failed. Verify GuC by "no
   `fetch failed` line" + `IOV` coming up + `echo 7 > sriov_numvfs`, never by that line.
3. **Adding the plain `.bin` files is what keeps GuC broken.**
   `drivers/base/firmware_loader/main.c:880-886` retries `.zst`/`.xz` **only when the
   plain-name attempt returned exactly `-ENOENT`**. i915 fetches uC firmware with
   `firmware_request_nowarn()` (`intel_uc_fw.c:757`; `FW_OPT_UEVENT|FW_OPT_NO_WARN`, so
   `nondirect=true` and compression is available). Our plain `.bin` returns `-EACCES` →
   the retry is skipped → the `.xz` that the kernel demonstrably CAN read is never tried
   (DMC and intel_vpu both loaded this boot from `.xz`-only names, same tree, and 7.2.8
   has `CONFIG_FW_LOADER_COMPRESS_XZ=y` + `# CONFIG_FW_LOADER_USER_HELPER is not set`).
   So `-EACCES` is not a new failure mode — it is the old one with our workaround
   standing in front of it. Also: §"Files touched" claims `recipes/recipe.yml` is
   untouched; the `xz -dk` step is `recipes/recipe.yml:145-159`.

**Still unexplained, and deliberately NOT fixed blind:** why an in-kernel read of that
plain file is `-EACCES` when `dd` as root reads all 320320 bytes of it. Ruled out with
evidence: SELinux (the loaded `system` class has no `firmware_load` — see
`/sys/fs/selinux/class/system/perms` — but the kernel logged "the above unknown classes
and permissions **will be allowed**", and there were only 3 AVCs this boot, none
firmware), IMA (`violations: 0`, `ima: No architecture policies found`), IPE
(`/sys/kernel/security/ipe/policies` empty), the loader itself (no `EACCES` anywhere in
`main.c`), and every per-file attribute (mode, ACL, owner, `lib_t`, xattr set —
identical to the blobs that do load). Still open: the read runs inside
`scoped_with_kernel_creds()` (subject becomes `kernel_t`, so SELinux's `fd:use` /
`system:firmware_load` targets are the FILE's SID), and the failing probe is ~1 s after
the ostree pivot — a pivot-timing / mount-namespace effect is not excluded.

**Two §8 items that also failed, for whoever picks this up:** `ausearch -m AVC -ts boot |
grep xenstored` is NOT empty (the `xend_var_lib_t:dir` write denial is back, so dd149b9's
local `.cil` install did not take on this boot), plus 2× `tuned_t capability2 mac_admin`

## 11. Reading the driver repo (strongtz/i915-sriov-dkms) — what it does and does not explain

Cloned both refs the image has ever built (`2026.09.16` = b42c0f8, `kernel-v7.2` =
8f9112d) and grepped them. Results, so nobody re-derives them:

1. **The fork neither ships nor requires special firmware.** No firmware install step
   in `dkms.conf`, `Makefile`, `PKGBUILD`, `debian/` or `i915-sriov-dkms.install`;
   `docs/` never mentions firmware (only `docs/secure-boot.md` for Debian-family
   signing). It expects plain distro `linux-firmware`. So "we need Intel's patched
   SR-IOV GuC blob" is NOT the issue.
2. **The EACCES is the kernel loader's, not the driver's.** `compat/` and `conftest.sh`
   never touch firmware loading (no `request_firmware`/`kernel_read_file` there), and the
   only `-EACCES` in the whole i915 tree is `intel_uc_fw_status_to_error()` mapping
   `INTEL_UC_FIRMWARE_UNINITIALIZED` — which is *not* the printing path. The log line we
   have is `gt_probe_error(gt, "%s firmware %s: fetch failed %pe", …)`
   (`intel_uc_fw.c:982` in both refs), and `%pe` renders the raw return of
   `firmware_request_nowarn()` at `intel_uc_fw.c:782`. Confirms §10's reading: the errno
   came from below the driver.
3. **NEW GATE, not in any handoff yet — `check_mtl_huc_guc_compatibility()`**
   (`intel_uc_fw.c:801`, MTL + HuC only): *"HuC 8.5.1 or newer requires GuC 70.7.0 or
   newer; older HuC binaries require GuC < 70.7.0"*, mismatch → `UNEXPECTED(...)` +
   `-ENOEXEC`. Our selected GuC is **70.53.0** ⇒ ≥ 70.7 ⇒ the HuC must be ≥ 8.5.1. If the
   distro `mtl_huc_gsc.bin(.xz)` is older, the boot that finally gets GuC loaded will die
   one step later with `-ENOEXEC` on the *HuC* — that is not a blob-on-disk bug and must
   not be chased as one. Expect either a matching HuC from a newer `intel-gpu-firmware`,
   or `i915.enable_guc=1` (submission only, no HuC auth) to get the display back.
4. Repo files worth stealing later: `i915-set-sriov-numvfs.conf` (their VF-count
   mechanism) and `docs/block-vfs.md` (the ADL/MTL "GuC rejects VFs without an admin
   override" failure that 10-03 §4 concluded on).

**Boot-path fact that changes the finalize recipe (§4's warning, made concrete):** the
Xen entry does not read BLS. `/usr/libexec/xen-dom0-refresh` regenerates
`/boot/grub2/user.cfg`'s `module2` line as *(`/proc/cmdline` minus a filter list)* +
a hardcoded tail `intel_iommu=on iommu=pt i915.enable_guc=3 i915.max_vfs=7
module_blacklist=xe ostree=<…> console=hvc0 console=tty0 rd.shell rw`, and it runs as
`ExecStopPost` of `ostree-finalize-staged.service` **from the currently booted tree at
shutdown**. Consequences: (a) a diagnostic karg added with `finalize --set karg+=` reaches
BLS and the *following* boots' Xen entry, but NOT the boot you are about to take — so for
one-boot instrumentation edit `/boot/grub2/user.cfg` directly (it is on the writable
`/boot`); (b) any arg in the booted `/proc/cmdline` that is not in the filter list is
carried forward automatically, so once it is in the Xen entry it persists; (c) the filter
list eats `i915.*`/`xe.*`/`console=*`/`rd.shell`/`rw` from the pass-through set — those
come only from the hardcoded tail.
