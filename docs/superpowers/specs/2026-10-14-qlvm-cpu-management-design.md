# qlvm CPU Management Design

Date: 2026-10-14

## Intent

Dom0 is currently unconstrained on a 14-core (6P+8E) / 65GB machine, leaving insufficient resources for guest VMs. Additionally, there's no way to control which physical cores guest VMs use on hybrid CPUs, and Xen's credit2 scheduler has a documented bias toward E cores that can degrade performance.

This design addresses two problems:

1. **Dom0 resource limits** — constrain dom0 memory and vCPUs via boot parameters so guests can allocate the rest.
2. **Guest CPU placement** — track which cores are in use and assign cores to VMs automatically (E-first) with manual override.

## Goals

- Dom0 gets a fixed, configurable amount of memory and vCPUs (defaults: 32GB, 2 vCPUs pinned to P cores).
- Guest VMs get explicit CPU core assignments, not just vCPU counts.
- Auto-placement fills E cores first, then P cores, to leave P cores available for performance-sensitive VMs.
- Per-VM manual override: pin specific cores in the VM's yaml.
- Core usage is tracked and persisted across reboots.
- `qlvm install` applies dom0 limits; no manual grub editing.

## Non-goals

- Credit2 weight tuning (skipped for now; pinning is more deterministic and avoids the E-core bias issue).
- Dynamic core migration (VMs stay pinned to their assigned cores for their lifetime).
- CPU pools (simpler to use direct vcpu-pin; pools add complexity and have SMT issues with credit2).
- SMT/hyperthreading awareness (the target CPU has no HT; if needed later, add sibling tracking).
- Per-vCPU pinning (assign a contiguous core range per VM; individual vCPU-to-core mapping is overkill).

## Anti-goals

- Don't make dom0 so starved that VM I/O stalls (2 vCPUs is the floor; increase if needed).
- Don't fragment cores across too many VMs (each VM gets a contiguous range).
- Don't break boot (dom0 params must be idempotent and safe to re-apply).

## Constraints

- **ostree/atomic dom0**: system packages and services belong in the ostree image recipe (`../os/`), not ad-hoc installs.
- **No shelling out**: use native Go control planes (xenlight for CPU pinning).
- **Generated boot config**: `/boot/grub2/user.cfg` is regenerated by `xen-dom0-refresh` on every boot and after ostree updates. Dom0 params must survive regeneration.
- **Xen sees flat CPUs**: no P/E concept in Xen; core type detection is done in qlvm from `/sys/devices/system/cpu/`.
- **Target hardware**: Intel Core Ultra 5 245K (6P cores 0-5, 8E cores 6-13, no HT, 65GB RAM). Design should work on any hybrid x86 CPU but is validated on this one.

## Decided Design

### 1. Dom0 resource limits

**Config file**: `/etc/qvm/qlvm.yaml` (existing) gets a new `dom0` section:

```yaml
dom0:
  memory_mb: 32768        # 32GB, default
  vcpus: 2                # pinned to first N P cores
  pin: true               # dom0_vcpus_pin boot param
```

**Application**: `qlvm install` writes Xen boot params to `/etc/qvm/xen-boot-params.conf`:

```
dom0_mem=32G,max:32G dom0_max_vcpus=2 dom0_vcpus_pin
```

**Boot param injection**: Modify `xen-dom0-refresh` (in `../os/files/system/usr/libexec/xen-dom0-refresh`) to read `/etc/qvm/xen-boot-params.conf` and append its contents to the `multiboot2` line:

```grub
multiboot2 /xen-4.21.2.gz $(cat /etc/qvm/xen-boot-params.conf 2>/dev/null)
```

The script change is minimal and safe: if the file doesn't exist, behavior is unchanged.

### 2. CPU core detection

At startup (or on demand), qlvm detects P vs E cores:

1. **Primary**: Read CPU model from `/proc/cpuinfo` and look up the known P/E split (maintain a small table of Intel hybrid CPU models and their core counts, e.g., "Ultra 5 245K": {p: 6, e: 8}).
2. **Fallback**: If the model is unknown, assume P cores are the first N in Linux CPU numbering (N is configurable via `dom0.cpu_hint` or defaults to half the cores).

**Why Linux CPU numbering works**: On all Intel hybrid CPUs, the kernel enumerates P cores first (cpu0, cpu1, ...) then E cores. The internal `core_id` values in `/sys/devices/system/cpu/cpu*/topology/core_id` are not sequential (P cores: 0,4,8,9,10,11; E cores: 12,13,14,15,16,20,24,28 on the target), but the Linux CPU number (the directory name) is sequential with P first.

**cpufreq is unavailable in Xen dom0** (para-virtualization), so frequency-based detection is not viable.

Cache the result; don't re-detect on every command. On the target CPU (Ultra 5 245K): cores 0-5 = P, cores 6-13 = E.

### 3. Core tracking

A new state file: `/var/lib/qvm/coremap.yaml`

```yaml
total_cores: 14
p_cores: [0, 1, 2, 3, 4, 5]
e_cores: [6, 7, 8, 9, 10, 11, 12, 13]
dom0:
  vcpus: 2
  cores: [0, 1]   # derived: dom0_vcpus_pin always pins to first N CPUs (which are P)
assignments:
  - vm: "work"
    cores: [6, 7]
  - vm: "browser"
    cores: [8, 9]
```

This tracks:
- Total CPU topology (P vs E split)
- Dom0's pinned cores (derived from the dom0 `vcpus` config field; `dom0_vcpus_pin` always assigns the lowest-numbered CPUs, which are P cores)
- Per-VM core assignments

The file is updated atomically on VM create/start/delete. It's the source of truth for "which cores are free."

**Staleness handling**: On VM create/start, if coremap.yaml lists a VM that doesn't exist on disk, treat those cores as free (rebuild from existing VM meta.yaml files + dom0 config). This handles out-of-band VM deletion.

### 4. Auto-placement algorithm

When a VM is created/started without explicit cores:

1. Load coremap.yaml.
2. Determine how many cores the VM needs (`vcpus` field).
3. Try to find a contiguous block of E cores of that size.
4. If not enough E cores, try a contiguous block of P cores (excluding dom0's cores).
5. If not enough of either, try mixing (E first, then P) — but prefer contiguous ranges.
6. Assign the cores, update coremap.yaml, write the pinning to the VM's meta.yaml.

**Contiguity preference**: `xl vcpu-pin` works with ranges like `6-9`, so contiguous blocks are simpler. If no contiguous block of the exact size is available, find the largest available block and use it (capping the VM's effective vcpus to what's available), or fail with a clear error.

### 5. Per-VM CPU config

**Meta struct** (`internal/vm/meta.go`) gets a new field:

```go
type Meta struct {
    // ... existing fields ...
    // Cores is the list of physical CPU cores this VM is pinned to.
    // Empty = auto-assigned (or no pinning if the host has no hybrid topology).
    Cores []int `yaml:"cores"`
}
```

**Create spec** (`internal/vm/create.go`) gets an optional `--cores` flag:

```bash
qlvm vm create work --cores 6-7    # manual pinning
qlvm vm create browser             # auto-placement (E first)
```

If `--cores` is provided, use those cores. Otherwise, run auto-placement.

**DomainSpec** (`internal/vm/domcfg.go`) gets a new field:

```go
type DomainSpec struct {
    // ... existing fields ...
    // CPUs is the core affinity mask for the domain (libxl cpus field).
    // Format: libxl cpu_mask or empty string for no pinning.
    CPUs string
}
```

The libxl mapping (`internal/vm/domcfg_libxl.go` or similar) sets the domain's CPU affinity based on `DomainSpec.CPUs`.

### 6. Core reclamation

When a VM is deleted or destroyed, its cores are freed back to the pool. The coremap.yaml is updated. Cores are not reclaimed when a VM is stopped (the assignment persists across stop/start cycles).

### 7. CLI surface

New/modified commands:

- `qlvm install` — applies dom0 limits (existing command, extended).
- `qlvm vm create <name> [--cores <range>]` — optional manual core assignment.
- `qlvm vm start <name>` — if cores not assigned, runs auto-placement.
- `qlvm cores` — new command showing the coremap:

```
$ qlvm cores
Core  Type  Assigned to
0     P     dom0
1     P     dom0
2     P     (free)
3     P     (free)
4     P     work
5     P     work
6     E     browser
7     E     browser
8     E     (free)
...
```

## What's left to the builder

- Exact format of `xen-boot-params.conf` (space-separated key=value pairs is the plan).
- How to handle coremap.yaml corruption (rebuild from running domains + dom0 config).
- Edge cases: VM with more vcpus than available cores, hotplug, VM migration.
- Unit tests for the placement algorithm.
- Integration with the existing VM lifecycle (create, start, stop, delete).
- Whether to detect hybrid topology automatically or require explicit config (default: auto-detect, config override possible).

## Research findings (for context)

- **Credit2 E-core bias**: credit2 (Xen default) piles VMs on E cores. On a 13900K: credit1 uses 27P/13E, credit2 uses 7P/33E. Pinning avoids this issue entirely.
- **Credit2 weights**: range 1-65535, default 256, proportional fair share. Skipped for this design.
- **Dom0 on P cores**: recommended. Dom0 handles VM I/O which is latency-sensitive. Default `dom0_vcpus_pin` gives dom0 the lowest-numbered cores (P cores on Intel).
- **Current load**: dom0 load average ~1.3 on 14 cores, 96% idle. 2 vCPUs is sufficient.
- **Xen boot params**: `dom0_mem=32G,max:32G` fixes memory, `dom0_max_vcpus=2 dom0_vcpus_pin` limits and pins CPUs.
