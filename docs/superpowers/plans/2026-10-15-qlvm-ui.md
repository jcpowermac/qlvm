# Plan: qlvm UI — Fyne desktop application for VM and template management

Handoff doc for a fresh session. Source-of-truth design spec:
`docs/superpowers/specs/2026-10-15-qlvm-ui-design.md`. Original design spec:
`docs/superpowers/specs/2026-09-26-qlvm-design.md`. Live-smoke pitfalls:
`AGENTS.md` (read "Xen / build", "OVSDB", "D-Bus", "Guest SSH / vm run",
"Podman" sections before touching anything here).

## Why

The qlvm CLI covers all VM and template operations, but a visual control
surface reduces friction for daily operations (start/stop/run app), makes
VM state and resource usage visible at a glance, and lowers the barrier to
template management. Qube Manager's layout (VM list + config panel) is the
reference design.

## Current state (verified 2026-10-15)

- **qlvm CLI:** complete cobra command tree in `internal/cli/`, wrapping
  internal packages: `vm`, `template`, `xenctl`, `ovn`, `ovs`, `config`,
  `coremap`, `setup`, `provisioner`, `projection`, `apps`.
- **Build:** `make container-build` compiles the cgo xenlight binding in a
  Fedora container (`Dockerfile.builder`), installs `qlvm` + `qlvm-vif` to
  `/usr/local/bin`. Builder pins Xen 4.21 headers to match dom0 runtime.
- **No GUI code exists yet.** This plan creates it from scratch.
- **Fyne:** not yet in `go.mod`. Needs to be added as a dependency.
- **Wayland:** dom0 runs SwayWM. Fyne's Wayland backend must be verified
  early (task 1 spike).

## Architecture (from spec §6)

- Single Go binary `qlvm-gui`, Fyne GUI toolkit
- Imports existing internal packages directly (no D-Bus, no subprocess)
- Runs as root; waypipe spawned with user's Wayland env
- Installs to `/usr/local/bin/qlvm-gui` via existing container build

## Pitfalls this feature specifically can step on

- **Fyne on Wayland/Sway:** Fyne's Wayland backend has been less mature than
  X11. Verify early (task 1) that Fyne renders and accepts input on Sway.
  Fallback if broken: XWayland, or reconsider toolkit.
- **Container build with Fyne:** Fyne is pure Go but uses cgo for some
  platform features. Must verify it compiles in `Dockerfile.builder`
  alongside the xenlight cgo binding. Fyne may need `pkg-config` or
  additional build dependencies in the builder image.
- **Xen version skew:** same as CLI — builder headers must match dom0
  runtime (currently 4.21). Fyne doesn't touch Xen, but the binary links
  xenlight, so the existing constraint applies.
- **Root + Wayland:** the UI runs as root but `vm run` needs the user's
  Wayland session. Must resolve env var passing (see spec §9 open questions).
  Test this early.
- **Long operations:** template bake (~5 min), install, provision take time.
  Must run in goroutines, update UI on the main thread (Fyne's `widget.Refresh`
  or channel-based updates), show progress.
- **No shelling out:** UI calls internal packages directly. The only exec is
  `waypipe` (same exception as CLI).
- **Ostree host:** `go build ./...` on the host may fail (missing headers).
  Use `make test` / `make lint` for unit work; `sudo make container-build`
  for installation.
- **Repo hygiene:** no vendor names, no real IPs, no shelling out to management
  CLIs.

## Code access notes (verified 2026-10-15)

The GUI calls existing internal packages directly. Most needed functions
are already exported:

- `template.Ensure()`, `template.LoadMeta()`, `template.NewPodman()`,
  `template.ReapBuilderContainers()` — all exported in `internal/template`.
- `xenctl.Start()`, `xenctl.Delete()`, `xenctl.New()` — exported in
  `internal/xenctl`.
- `vm.Create()` — exported in `internal/vm` with `CreateDeps` + `Spec`.
- `setup.Run()` — exported in `internal/setup`, takes `*setup.Plan`.
- `provisioner.Provision()`, `coremap.Load()`, `apps` functions — exported.

**One refactor required:** `stopForced()` (graceful stop + force-kill
fallback with ~60s poll) is private in `internal/cli/lifecycle.go`. Move it
to `internal/xenctl` as `xenctl.StopForced(x Xen, name string) error` so
both the CLI and GUI can use it. The CLI's `startVM()` is also private but
wraps `xenctl.Start()` directly, so no export needed — the GUI calls
`xenctl.Start()` the same way.

**Install plan construction:** `newInstallPlan()` in `internal/cli/install.go`
constructs the `setup.Plan` with real control planes (OVN, OVS, FW, Netd,
SD, Storage, Dom0Params, VifScript, SaveCfg). The GUI replicates this
construction (or it could be exported from a shared location — builder
decision, minor).

## Tasks

### Task 1: Fyne spike — verify Wayland + build integration

**Goal:** Confirm Fyne works on Sway and compiles in the container build.

1. Add `fyne.io/fyne/v2` to `go.mod` (use `go get` in the container, not host).
2. Create `cmd/qlvm-gui/main.go` with a minimal Fyne window (title "qlvm",
   a label, a button that prints to a log widget).
3. Verify the container build compiles it:
   - Add `qlvm-gui` to the build targets in the Makefile.
   - Run `sudo make container-build`.
   - Check for cgo/linker errors (Fyne may need additional build deps in
     `Dockerfile.builder`).
4. Install and launch on the dom0: `sudo qlvm-gui` from a Sway session.
5. Verify: window renders, buttons work, input works, no Wayland errors.
6. If Fyne fails on Wayland: document the failure, try XWayland, decide on
   fallback (XWayland wrapper, different toolkit, or accept the limitation).

**Definition of done:**
- `sudo make container-build` succeeds with `qlvm-gui` included.
- `sudo qlvm-gui` opens a responsive window on Sway.
- Build integration documented (any new `Dockerfile.builder` deps).

### Task 2: Project structure and shared UI utilities

**Goal:** Establish the GUI code layout and reusable components.

1. Create package structure under `internal/gui/`:
   - `internal/gui/app.go` — Fyne app setup, window creation, main loop
   - `internal/gui/vmlist.go` — VM list widget and data model
   - `internal/gui/vmconfig.go` — VM configuration panel
   - `internal/gui/templates.go` — template list and details
   - `internal/gui/createvm.go` — create VM dialog
   - `internal/gui/createtpl.go` — create template dialog
   - `internal/gui/logpane.go` — collapsible log/output widget
   - `internal/gui/cores.go` — CPU cores view
   - `internal/gui/operations.go` — long-running operation runners (goroutine + UI updates)
   - `internal/gui/state.go` — shared UI state (selected VM/template, refresh logic)
2. Create shared utilities:
   - State formatting helpers (bytes → MB, core lists → string)
   - Confirmation dialog helper (for delete operations)
   - Progress bar helper (for long operations)
   - Error display helper (consistent error dialogs/toasts)
3. Wire `cmd/qlvm-gui/main.go` to `internal/gui/app.go`.

**Definition of done:**
- Package structure compiles (`go build ./...` in container).
- Main window opens with placeholder panes (left: empty list, right: empty panel).
- Shared utilities are unit-tested where applicable.

### Task 3: VM list view

**Goal:** Display VMs with name, type, state, memory, vCPUs; support selection and refresh.

1. Implement `internal/gui/vmlist.go`:
   - Data model: `[]VMRow` with Name, Type, State, MemoryMB, VCPUs.
   - Data source: call `xenctl.New()` + `xenctl.List()` for running VMs,
     scan `/var/lib/qvm/vms/*/meta.yaml` for stopped VMs (same logic as
     `internal/cli/lifecycle.go:listCmd`).
   - Fyne widget: `widget.List` or `widget.Table` with columns.
   - Visual distinction for running VMs (color dot or background).
   - Selection callback: notify `state.go` of selected VM.
2. Implement refresh logic in `internal/gui/state.go`:
   - Manual refresh button.
   - Auto-refresh timer (2s for running VMs, 30s for stopped).
   - Refresh must not block the UI (run in goroutine, update on main thread).
3. Implement filter/search: text box filtering the list by name.

**Definition of done:**
- VM list shows all VMs (running + stopped) with correct state.
- Selecting a VM highlights the row and updates the right pane (placeholder).
- Refresh button updates the list.
- Auto-refresh detects state changes (start/stop from CLI appears in UI).
- Filter box filters the list.
- Unit tests for data source logic (fake xenctl + meta files).

### Task 4: VM configuration panel

**Goal:** Show selected VM's full configuration in the right pane.

1. Implement `internal/gui/vmconfig.go`:
   - Load VM meta from `/var/lib/qvm/vms/<name>/meta.yaml` via `vm.LoadMeta`.
   - Display fields (read-only):
     - Identity: Name, Type, Domain, IP, MAC, UUID
     - Resources: Memory, vCPUs, Cores (pinned), Workspace Size
     - Storage: Template ref, Image, Digest, Mounts (list)
     - Status: Created time, State
   - Layout: Fyne `container.NewBorder` or `layout.Form` for grouped fields.
2. Handle "nothing selected" state: show empty panel with "Create VM" button.
3. Handle "VM deleted" state: if selected VM disappears on refresh, clear
   the panel.

**Definition of done:**
- Selecting a VM shows its complete configuration in the right pane.
- All fields match the CLI's `vm list` output and meta.yaml content.
- Empty state and deleted-VM state handled gracefully.
- Unit tests for meta loading and field formatting.

### Task 5: Action buttons and VM lifecycle operations

**Goal:** Implement Start, Stop, Kill, Restart, Delete buttons with proper error handling.

1. Implement action bar with context-sensitive buttons:
   - Show/hide buttons based on VM state (e.g., Start hidden for running VMs).
   - Disable buttons during long operations.
2. Implement each operation in `internal/gui/operations.go`:
   - **Start:** call `xenctl.Start()` (same path as CLI's `startVM`).
   - **Stop:** call `stopForced()` logic (graceful + force-kill fallback,
     ~60s poll).
   - **Kill:** call `xenctl.Destroy()`.
   - **Restart:** stop + start sequence.
   - **Delete:** confirmation dialog, then `xenctl.Delete()` (same path as
     CLI's `deleteCmd`).
3. Each operation:
   - Runs in a goroutine.
   - Shows a progress indicator while running.
   - Updates the VM list and config panel on completion.
   - Shows errors in the log pane and/or a dialog.
4. Wire buttons to operations.

**Definition of done:**
- All five lifecycle operations work from the UI.
- Operations update the UI state (list, config panel) after completion.
- Errors are displayed clearly.
- Delete requires confirmation.
- Stop handles the zombie case (force-kill after timeout).
- Unit tests for operation logic (fake xenctl).

### Task 6: Template view

**Goal:** Display templates in a separate tab/view with details.

1. Implement `internal/gui/templates.go`:
   - Add "Templates" tab to the left pane (alongside "VMs").
   - Data source: scan `/var/lib/qvm/templates/*/` for META files,
     call `template.LoadMeta` for each (same logic as CLI's `template list`).
   - Display: template dir, image ref, digest, size, kernel version,
     count of VMs referencing it, completeness status.
   - Selection: show template details in the right pane.
2. Template details panel:
   - Image ref, digest, kernel, size.
   - Referencing VMs (list of VM names that use this template).
   - Status: complete/incomplete (warn on incomplete).
   - Action button: Delete (with confirmation, refuse if VMs reference it).
3. Template delete operation:
   - Confirmation dialog.
   - Check for referencing VMs (refuse if any).
   - Call template delete logic (same as CLI's `template delete`).
   - Update the list.

**Definition of done:**
- Templates tab shows all templates with correct metadata.
- Selecting a template shows its details and referencing VMs.
- Template delete works (with reference check).
- Incomplete templates are visually flagged.
- Unit tests for template listing and reference checking.

### Task 7: Create VM dialog

**Goal:** Implement the full VM creation flow from a dialog.

1. Implement `internal/gui/createvm.go`:
   - Dialog layout:
     - Name: text input (required, validated for valid domain name chars).
     - Template: dropdown populated from available templates (task 6 data).
     - Domain: dropdown populated from config domains (`config.Load`).
     - Type: dropdown (app/disposable/agent; agent auto-selected if template
       is agent).
     - Memory: number input (default from config, min 64).
     - vCPUs: number input (default from config).
     - Workspace size: number input (agent VMs only, default 4096).
     - Mounts: list widget with add/remove rows (host path, guest path).
     - Cores: text input (optional, e.g., "6-7" or "6,7,8").
   - Validation: required fields, valid values (same as CLI's create
     validation).
2. Create operation:
   - Run `vm.Create()` in a goroutine (same path as CLI's `createCmd`).
   - Show progress during creation (OVN port, reflink, meta write).
   - On success: add VM to the list, select it, show config panel.
   - On error: show error in log pane/dialog.
3. Template auto-detection: if selected template is agent type, auto-set
   type to agent (same logic as CLI).

**Definition of done:**
- Create VM dialog shows all fields with correct defaults.
- Validation catches missing/invalid input.
- VM creation works end-to-end (OVN port, reflinked disk, meta.yaml).
- New VM appears in the list and is selected.
- Mounts and cores work.
- Unit tests for validation and create path (fake deps).

### Task 8: Create Template dialog

**Goal:** Implement template baking from a dialog with progress tracking.

1. Implement `internal/gui/createtpl.go`:
   - Dialog layout:
     - Image ref: text input (e.g., `quay.io/fedora/fedora:44`).
     - Force re-bake: checkbox.
   - Validation: non-empty ref, valid image ref format.
2. Create operation:
   - Run template bake in a goroutine (same path as CLI's `template create`).
   - Show progress bar and streaming log output (image-builder logs,
     ostree bake progress).
   - Operation takes ~5 minutes — must not block UI.
   - On success: add template to the list, select it.
   - On error: show error, clean up partial state (same reaping logic as CLI).
3. Force re-bake: if template dir exists, show warning; `--force` behavior
   (refuse if VMs reference it, otherwise remove + re-bake).

**Definition of done:**
- Create Template dialog accepts image ref and force flag.
- Bake runs in background with progress and log output.
- UI remains responsive during the 5-minute bake.
- New template appears in the list.
- Force re-bake works with reference checking.
- Unit tests for bake path (fake podman/bake).

### Task 9: Run App (waypipe) integration

**Goal:** Implement `vm run` from the UI, handling the root/Wayland split.

1. Resolve the Wayland env question (spec §9):
   - Test launching `sudo qlvm-gui` from Sway: does it inherit
     `WAYLAND_DISPLAY` and `XDG_RUNTIME_DIR`?
   - If not, implement one of: (a) read from loginctl, (b) require env at
     launch, (c) pkexec with env passing.
   - Document the chosen approach.
2. Implement Run App button:
   - Only shown for running VMs.
   - App picker dialog: list cached desktop entries from
     `/var/lib/qvm/desktop-cache/<vm>/` (use `internal/apps` package).
   - If no cache: prompt to sync first (`apps sync`).
3. Run operation:
   - Spawn `projection.Run()` with waypipe (same path as CLI's `runCmd`).
   - Run waypipe with the user's Wayland env (not root's).
   - waypipe runs as the user, not root (drop privileges for the spawn).
   - Handle errors (VM not running, no waypipe, no Wayland session).
4. Apps sync button:
   - Per VM: sync that VM's desktop cache.
   - All running: sync all running VMs.
   - Use `internal/apps` package (same as CLI's `apps sync`).

**Definition of done:**
- Run App button shows app picker with cached desktop entries.
- Selected app launches in the VM via waypipe on the dom0 Wayland session.
- Waypipe runs with correct user env (verified on Sway).
- Apps sync works (per VM and all running).
- Errors handled (VM down, no cache, no Wayland).
- Live-tested on Sway with a real VM.

### Task 10: Provision, Sync Kernel, Install, Cores

**Goal:** Implement the remaining operations.

1. **Provision button:**
   - Run `provisioner.Provision()` (same path as CLI's `provisionCmd`).
   - Show progress (sftp transfer).
   - Update log pane.
2. **Sync Kernel button:**
   - Run kernel sync (same path as CLI's `sync-kernel`).
   - Show progress.
3. **Install Dom0 button:**
   - Run `setup.Run()` (same path as CLI's `installCmd`).
   - Long operation — progress bar + log output.
   - Requires config validation first.
4. **Cores view:**
   - Button in menu or action bar.
   - Show CPU topology (P/E cores), dom0 assignment, VM assignments, free cores.
   - Use `internal/coremap` package (same as CLI's `coresCmd`).
   - Modal dialog or separate tab.

**Definition of done:**
- All four operations work from the UI.
- Output/progress shown in log pane.
- Cores view matches CLI's `qlvm cores` output.
- Unit tests for each operation path.

### Task 11: Log pane and UX polish

**Goal:** Implement the collapsible log pane and polish the overall UX.

1. **Log pane:**
   - Collapsible bottom panel (toggle button).
   - Monospace font, scrollable.
   - Shows output from all long operations (template bake, install,
     provision, create).
   - Clear button.
   - Timestamped entries.
2. **UX polish:**
   - Consistent button styling and placement.
   - Tooltips on all buttons and fields.
   - Error dialogs with actionable messages (matching CLI error messages).
   - Confirmation dialogs for destructive operations (delete VM, delete
     template, install).
   - Loading indicators during operations.
   - Window title shows app name + selected VM (if any).
   - Keyboard shortcuts (R for refresh, F5 for refresh, Esc for dialogs).
3. **State persistence:**
   - Remember window size/position across launches (Fyne's app.Preferences).
   - Remember last selected VM/tab.

**Definition of done:**
- Log pane captures and displays operation output.
- All UX elements are consistent and responsive.
- Keyboard shortcuts work.
- Window state persists across launches.
- Manual UX review on Sway.

### Task 12: Integration testing and documentation

**Goal:** End-to-end testing and user documentation.

1. **Integration tests:**
   - Full lifecycle: create template → create VM → start → run app → stop
     → delete VM → delete template, all from the UI.
   - Error cases: create VM with invalid template, delete referenced
     template, run app on stopped VM.
   - Concurrent operations: start two VMs simultaneously.
   - Refresh behavior: start VM from CLI, verify UI updates.
2. **Documentation:**
   - Add UI section to `README.md` (launch, basic usage, privilege model).
   - Document the Wayland env requirement for `vm run`.
   - Document build/install: `sudo make container-build` installs `qlvm-gui`.
   - Add to `AGENTS.md` pitfalls if any UI-specific issues found.
3. **Makefile:**
   - Ensure `qlvm-gui` is in the default build target.
   - Add `make gui` shortcut if desired.
4. **Desktop integration:**
   - Create `/usr/share/applications/qlvm-gui.desktop` for Sway launcher
     (rofi/dmenu).
   - Icon (simple, generated or minimal SVG).

**Definition of done:**
- Full lifecycle works end-to-end from the UI.
- Error cases handled gracefully.
- README updated with UI usage.
- Desktop entry installed.
- `sudo make container-build` installs both `qlvm` and `qlvm-gui`.
- Manual sign-off: all CLI operations accessible from the UI.

## Execution order

Tasks are sequential with dependencies:

1. **Task 1** (spike) must pass before any other work — if Fyne fails on
   Wayland, the whole plan changes.
2. **Task 2** (structure) before any view work.
3. **Tasks 3-4** (VM list + config) can start in parallel after Task 2.
4. **Task 5** (lifecycle ops) after Tasks 3-4.
5. **Task 6** (templates) can start after Task 2 (independent of VM list).
6. **Task 7** (create VM) after Tasks 3-4-6 (needs list + template data).
7. **Task 8** (create template) after Task 6.
8. **Task 9** (waypipe) after Task 5 (needs running VMs) + Wayland env
   resolution.
9. **Tasks 10-11** after all operations are implemented.
10. **Task 12** last.

Estimated effort: Task 1 (1-2 hours), Task 2 (2-3 hours), Tasks 3-11
(4-8 hours each), Task 12 (2-3 hours). Total: ~2-3 weeks of focused work.

## Builder check questions (resolved)

Reviewed the plan as a fresh builder. Questions sorted into three piles:

**Answered by code/conversation:**
- All core operation functions are exported (verified above). GUI calls them
  directly — no D-Bus, no subprocess.
- `stopForced()` needs a small refactor to `internal/xenctl` (noted above).
- Install plan construction is replicable from `internal/cli/install.go`.

**Builder calls (minor, don't change what gets built):**
1. **Fyne version:** latest stable (`fyne.io/fyne/v2`).
2. **Window min size:** 900x600.
3. **Auto-refresh interval:** 2s running, 30s stopped.
4. **Editable VM config:** read-only display only (no in-place edits; CLI
   has no `vm update`).
5. **Log pane default state:** collapsed.
6. **Error display:** dialog for critical errors, log pane for operation output.
7. **Desktop entry name:** "qlvm GUI".
8. **Install plan location:** replicate in GUI package (don't refactor CLI).

**Needs user input (changes implementation):**
1. **Wayland env for waypipe:** when the UI runs as root, how does it get the
   user's `WAYLAND_DISPLAY` and `XDG_RUNTIME_DIR`? Will test during Task 1
   spike by launching `sudo qlvm-gui` from Sway. If env is inherited, no
   additional work. If not, options: (a) require env at launch (`sudo
   WAYLAND_DISPLAY=$WAYLAND_DISPLAY qlvm-gui`), (b) read from loginctl,
   (c) pkexec with env passing. Resolution needed before Task 9.
2. **Privilege dropping for waypipe:** waypipe must run as the user, not root.
   Mechanism: (a) `os.Setuid()` to user UID before exec (simplest, but
   requires knowing the target UID), (b) `pkexec --user <user> waypipe ...`
   (adds a polkit dependency), (c) spawn a user-session helper that runs
   waypipe. Builder preference: (a) with UID from the env or `SUDO_USER`.
   Confirm this is acceptable.
